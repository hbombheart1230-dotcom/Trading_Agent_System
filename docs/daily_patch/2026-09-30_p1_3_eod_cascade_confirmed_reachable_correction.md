## Correction

The prior pass's "no evidence appeared that the end-of-day sequence actually ran" conclusion was caused
by an error in **how the result was checked**, not by any defect in the runtime. That check looked for
`state["persisted_state"]["processed_market_status_action_keys"]` (a nested lookup). The actual on-disk
`data/state.json` written by this frozen SHA stores these fields at the **top level** of the JSON
document (`state["processed_market_status_action_keys"]`, `state["kiwoom_market_status"]`,
`state["last_market_status_closeout_result"]`) -- `persisted_state` is only ever an empty `{}` in the
saved file. Re-reading the exact same state file this pass already produced, using the correct top-level
keys, shows the cascade completed successfully:

- `kiwoom_market_status`: the injected event, verbatim.
- `processed_market_status_event_ids`: contains the injected event's id.
- `processed_market_status_action_keys`: `["2026-09-30:regular_close"]`.
- `last_market_status_closeout_result`: `{"event_id": "...", "code": "4", "trigger": "kiwoom_market_status_4", "ok": false}` (a handled negative result, same `SOURCE_MINUTE_HISTORY_MISSING`-class pattern already characterized earlier this session for isolated/mock days -- not a crash).
- `reports/operator_summary/daily/2026-09-30/closeout_maintenance.{json,md}` and 148 total report
  artifacts were generated by the cascade, all present on disk.

## Call-path trace (read-only)

`scripts/run_session.py` (`--mode live --phase intraday`, no `--probe`/`--simulated`) resolves to
`implementation_id="m13_live_loop"` -> `libs/runtime/entrypoints/m13_live_loop.py::main()`, which passes
`run_once_fn=graphs.pipelines.m13_live_loop.run_m13_once` into
`libs/runtime/live_loop_runner.py::run_live_loop()`. Inside `run_live_loop`'s main loop, `run_once_fn`
is called unconditionally on every iteration once the lock/ownership guards pass (no `--session-hard-gate`
is set by the Docker image's default CMD, only `--allow-offhours`). `run_m13_once()` itself calls
`market_status_fn` (`apply_market_status_closeout_events`) **before** `tick_fn` (`run_m13_tick`, the
function that actually branches on `--tick-pipeline legacy_m10` vs `integrated_chain` and where any
trading-session-hours gating for the full decision pipeline lives) and before `eod_fn`
(`run_m13_eod_report`, a separate, unrelated once-per-day report trigger). Market-status closeout
processing is therefore **upstream of and independent from** both the `--tick-pipeline` selection and any
trading-session gate -- it runs every tick, regardless of `integrated_chain` vs `legacy_m10`, and
regardless of whether the market is currently open.

The `KiwoomMarketStatusListener` (started as a background daemon thread by `run_live_loop`, not a
separate process) only ever calls `record_market_status_events()` -- it contains no closeout logic of its
own. All closeout execution is the tick loop's responsibility, fully decoupled from whether the listener
ever obtains a real, live token (in the original 6h47m isolated mock soak, it never did -- no
`KIWOOM_APP_KEY`/`KIWOOM_APP_SECRET`, so no real event was ever produced; that soak's own
`EOD_CASCADE_EXECUTED = NO` conclusion, reached independently via the same corrected top-level check,
is confirmed still accurate for that specific run -- it genuinely never received a close event, which is
different from this pass's finding that the mechanism itself works once given one).
